# 階段性成果 — 2026-08-25

## 一句話結論

**三條線（DevOps / DataOps / MLOps）全部打通並且每一道閘門都被實際測過會擋人；
剩下三個紅燈，其中兩個不是工程問題。**

平台在一台 MacBook 上，資料從政府開放 API 一路走到模型預測。
**31 個里程碑，28 個具備可重跑的證據**——不是文件說有，是指令跑得出來。
剩下 2 紅 1 未開始，下面逐條列出，不修飾。

---

## 為什麼這份報告可以信

這個專案一路上最常犯的錯，是**「註解描述了一個機制，就當作那個機制存在」**。
已經抓到 5 次以上。所以本階段的驗收方式改成：

> **每一道新加的檢查，都刻意弄壞一次，確認它真的會擋。**

本階段共注入 **12 次**刻意破壞（突變測試）。
其中 **11 次當場被抓到；1 次沒有**——而那 1 次沒抓到，才是最有價值的一次：
它證明我寫的那條斷言根本沒有執行。補強後才真的會擋。
弄壞的檔案一律在 `finally` 還原，並以雜湊確認 byte-exact。

抓到的例子，兩個都不是靠 code review 發現的：

- **佔位符撞名**：藍綠部署的 template 用裸的 `SCHEMA_VERSION`，`sed` 連
  `EXPECTED_SCHEMA_VERSION` 裡面也一起換掉，產生 `EXPECTED_99=99`。
  結果一個**刻意做壞的 green 回報 ready 並被放行**。
- **`readyReplicas` 會騙人**：rollout 卡住時舊世代的 pod 仍然 Ready 且被計入，
  所以新 pod 永遠起不來的 green 照樣顯示 2/2。改查 `updatedReplicas` 才是對的。

### DevOps — 10 / 10

  每一項都是「做一個動作」而不是「讀一個設定」——PVC 真的綁定並寫入、
  image 真的推送並**由節點拉取**。

  rolling 沒有任何一刻可以說「不對，退回去」。

**四道閘門**（`promote.sh`），前三道存在的理由都是「不要相信快取的狀態」：

1. 現行 template 的副本數（不是 `readyReplicas`）
2. **當下**直接問每個 pod `/health/ready`
3. pod 認定的 schema 與資料庫實際 schema 必須相等
4. 切換後 endpoints 不得為空

### DataOps — 10 / 11

**650 萬列事實資料**，粒度從縣市×週到村里×年，全部帶血緣。

- 血緣算術是**資料庫 CHECK 約束**：`in_file = accepted + rejected + duplicate`，
  32 個檔案全數成立。對不上就寫不進去。
- **分母到位**，所以鄉鎮率算得出來：石岡區 43.2/10萬 對 大安區 28.1/10萬。

- COVID 只有 2021 年起的 90,373 列，**沒有補零**——缺席不等於零。

## 本階段修掉的三件事（都是「看起來在運作，其實沒有」）

### 1. 排程重訓從來沒有自己跑過

C9 原本記成完成，理由是「已進設定檔且實跑成功」。兩半分開看都是真的，
**合起來不成立**：設定檔有一筆，不等於作業系統有一個排程。
實查是 `MISSING` / `NEVER FIRED`——**每一次「成功的」重訓都是手動打的**。

補證方式刻意不是等到週日，也不是用 `launchctl kickstart` 充數
（kickstart 一樣會讓板子翻綠，但它只證明「叫得動」，不證明**日曆會觸發**）。
改成把日曆條目暫時移到 3 分鐘後，讓系統**自己**觸發，再還原：

```
trigger=scheduled  status=ok  251s  1 published, 1 refused
plist 還原 byte-exact，日曆確認回到 週日 06:20
```

### 2. 每天紅燈的安全掃描，掃的是已經退役的目標

DAST 每天報「develop 沒開？」，指向一個**退役好幾天**的服務。
compose 還在 publish 那個 port，所以失敗長成最會誤導人的形狀：
**TCP 連得上、TLS 握手直接斷**。port 有回應，後面沒有東西。

已改指向真實的服務介面。首次實掃：**HIGH=0 MEDIUM=0 LOW=1**，閘門設在 MEDIUM。

### 3. 還原演練把備份的錯怪錯了對象

演練報「還原後讀不到秘密」，紅了三天。實際上還原是成功的（讀到 93 字元），
是**對照組**那一側沒有回應。一個專門回答「備份還原得回來嗎」的檢查，
花三天回答「不行」，而且理由在比較的另一邊。

現在不可比的情況有自己的訊息，指向真正壞掉的那個元件。

## 三個紅燈（誠實列出，不修飾）

| # | 項目 | 性質 | 誰能解 |
|---|---|---|---|
| B10 | 流行病學週 ↔ 日曆日對不上 | **不是工程問題** | 只有疾管署 |
| C8 | 模型沒有贏過天真基準 | **不是 bug，是研究結果** | 需要更好的特徵 |
| — | 三把秘密沒有輪替紀錄 | 需要決策，會動到活憑證 | 使用者 |

### B10 — 阻斷中

`time_period` 有 1,024 個週期間，`cal_date` **全為 NULL**。
所以週資料與日資料無法在時間軸上 join。
這不是寫不出來，是**週的定義本身要向疾管署查證**（52 週還是 53 週）。
中醫大資料送來時會對不上，所以這是硬前提不是待辦。

### C8 — 未達成，而且這是誠實結果

模型目前多數情況**輸給「假設下週跟這週一樣」**：
t+1 輸 12%，t+2 只贏 0.3%（雜訊等級）。
唯一有內容的數字是**方向準確率 63.8%**。

這不是待修的 bug。週 %ILI 高度自相關，持平是很強的基準。
現有特徵**全是縣市級落後指標**（開放資料落後約 2 週），
天花板就是生態層級推論——說得出「台中市這週會怎樣」，
說不出「哪一群人、哪一家醫院會先滿載」。

**突破口是 C10（中醫大個人級 + 醫院級資料）**，而它有三個硬前提，
其中兩個就是 B10 與測試資料遮蔽（見 `docs/Backlog.md` §7）。

### 秘密輪替 — 等決策

三把秘密（`devops/ghcr`、`devops/github`、`devops/grafana-admin`）
**完全沒有輪替紀錄**。沒有自行處理，因為那會動到活憑證。

本階段把「90 天」這個寫死的數字改成**每把秘密自己的資料**：
一把 `write:packages` 的 classic PAT 和一把只在本機 loopback 用的 Grafana 密碼，
不該被同一個數字管。豁免也是**記錄下來的決策**（必須寫理由），
不是靜靜地從清單消失，也不是蓋一個假日期把燈弄綠。
