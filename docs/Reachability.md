# 可達性：為什麼要它，它證得到什麼，證不到什麼

## 目的不是整潔

可達性在這個 repo 裡要防的是兩件事，而第二件是第一件的直接後果：

> **孤兒功能** → 找不到 → **下一個人（或下一隻 agent）再寫一支** → **重複開發**

「整潔」是副作用，不是理由。**如果整潔是理由，第一次趕時間就會被放棄。**

第二個目的是**三種讀者**：程式、agent、人類，都要能從 `README.md` 出發，
找到某個功能的**位置、目的、敘述**。這三種讀者對「找得到」的定義不同，
而其中一種的限制決定了規則的形狀：

- **人類**可以搜尋、可以問人、可以憑印象
- **agent** 只能跟連結。**它跟不了反引號，也跟不了散文**
- **程式**只能跟結構

所以 `` `platform/nginx/README.md` `` 這種寫法**在人類那一層勉強可用，在另外兩層等於不存在**。
2026-09-02 的盤點裡，五個孤兒文件全部是同一個成因：
**這棵樹存在於散文裡，不存在於連結裡。**

## 四層，每一層證的是不同的東西

| 層 | 工具 | 問題 | 失敗的樣子 |
|---|---|---|---|
| 1. 文件可達 | [`doc_graph.py`](../platform/docs/doc_graph.py) | 從 README 點得到這份文件嗎 | 五份孤兒文件，其中一份是**第二份、過期的**能力索引 |
| 2. 頁面出處 | [`doc_freshness.py`](../platform/docs/doc_freshness.py) | 這頁是產生的，還是有人用手承諾它是真的 | 兩份手工現況頁，一份對長官說反了平台最近投入最多的地方 |
| 3. 功能可達 | [`capability_graph.py`](../platform/docs/capability_graph.py) | 從 README 找得到這支能力、而且知道它做什麼嗎 | 89 支裡 9 支找不到，**其中四支是人要手動執行的** |
| 4. 重複偵測 | [`duplicate_check.py`](../platform/docs/duplicate_check.py) | 有沒有兩份東西在講同一件事 | 八張圖存在兩套、完全分岔，**而兩套都在文件裡、都找得到** |

**第四層存在的理由，就是前三層的邊界。**
可達性防的是「找不到 → 再寫一支」。它**防不了**「兩份都找得到、都有人維護、但已經分岔」——
而那個才是 2026-09-02 真正發生的事，且後果更嚴重：
長官在板面上看到一種架構，在簡報裡看到另一種，**兩份都標著現況**。

## 每一層證不到什麼（這一節比上一節重要）

- **第 1 層證不到內容是真的。** 傷最重的那份文件從 README 連得到、被標成「先看這份」，
  而它是錯的。**可達性給它滿分。**
- **第 2 層證不到寫得好。** 它只能驗「有沒有生產者」與「生產者的 `--check` 過不過」。
  一份產生式但邏輯錯誤的頁面，它一樣放行。
- **第 3 層證不到描述得好。** 規則是結構性的：那個提及必須落在一列**至少三欄**的表格裡
  （何時跑／做什麼／保證什麼）。**機器能驗那三欄存在，驗不了它們寫得好不好**，
  這份檔案也不假裝可以。它買到的是：**再也不可能不小心地把一支能力加進來卻什麼都不說。**
- **第 4 層只做正規化後的完全比對，刻意不做相似度評分。**
  相似度的門檻是「披著數字外衣的判斷」，會產生誤報，而**誤報是一個檢查被靜音的方式**。
  代價是漏抓，這是正確的犯錯方向。
  另外「同一產物兩個生產者」那個訊號**只報告、不判定失敗**——
  它以檔名比對，分不出「寫」與「讀」，已知的良性碰撞直接記在檔案裡而不是偷偷過濾掉。

## 豁免必須有理由，而理由本身要被檢查

四層都有豁免機制，而四層的豁免都要求一句話。**沒有理由的豁免，和「有人把它靜音了」分不出來。**

第 3 層的豁免多一道：內部元件可以指向它所屬的入口，
**而那個入口本身必須是被描述的**。少了第二半，`INTERNAL` 就變成藏東西的地方。

## 空集合一律拒答

四支工具都有下限，低於下限就 **exit 2 拒絕產出報告**，而不是回報「沒有發現問題」。

理由是這個 repo 反覆遇到的同一件事：
**「0 個孤兒（走訪了 3 份文件）」讀起來和「0 個孤兒（走訪了 62 份文件）」一模一樣。**
空集合上的「每一個都合規」是恆真句，不是驗證結果。

## 邊界：這個 repo 的能力索引 vs AIS registry

這兩份**不是兩份索引**，不該合併。分界是**跨不跨工具邊界**：

| | AIS `capabilities/registry.yaml` | 這個 repo 的能力表 |
|---|---|---|
| 管什麼 | **跨 AI 工具**的能力：任何一隻 CLI（claude / grok / agy / hermes…）都該找得到並能 `verify` | **單一 repo 的內部組件**：只有在這個 repo 的脈絡裡才有意義 |
| 規模 | 17 筆 | 90 支 |
| 索引形式 | 手寫 YAML，強制 `verify` 指令 | **產生式** `evidence/capabilities.json`（由 `capability_graph.py --catalog` 從 README 表格抽出） |
| 判準 | 「別的 AI 需要用到它嗎」 | 「這個平台自己需要它嗎」 |

**把 90 支全部登記進 AIS registry 是錯的**：它會從 17 筆變成 100+ 筆，
而一份 100+ 筆的清單沒有人看——那正好製造出這份文件要防的東西。
目前只有 `devops-k8s-cluster` 一筆跨界（因為叢集是別的工作也會用到的基礎設施），
那個判準是對的。

**新增能力時的判斷順序**：先問「別的 AI 工具需要直接呼叫它嗎」。
是 → AIS registry（含 `verify`）；否 → 這個 repo 的能力表。**兩邊都登記是錯的**，
那就是自己造一份會分岔的副本。

## agent 那一層：機器可讀的總表是產生的，不是手寫的

```bash
python3 platform/docs/capability_graph.py --catalog   # -> evidence/capabilities.json
```

每一筆是 `path` / `when` / `what` / `guarantee` / `described_in` / `run`，
**全部從 README 的能力表抽出來**。

手寫的清單會過期，而**過期的清單讀起來和正確的清單一模一樣**——
這就是 `platform/README.md` 曾經那份第二索引出事的方式。
產生式的做法讓總表**不可能**在文件沒改的情況下分岔。

## 工具會換掉，那時候還剩下什麼

這一節是為了幾年後還在維護這個 repo 的人寫的——包括幾年後的我們自己。

**會先腐爛的（工具形狀的東西）**：

- 具體選型（Loki／ELK／SigNoz、Prometheus／VictoriaMetrics、k3s／別的發行版）
- 設定格式（`config.alloy` 的語法、compose 檔、版本釘選、CLI 旗標）
- 查詢語言與綁在它上面的儀表板與告警規則

**這些全部會過期，而且過期得比想像快。** 這個 repo 半個月內就把
「Kubernetes 不導入」反轉、把 ELK 那一格的理由修正過一次。

**不會腐爛的，只有三樣，而且全部與工具無關：**

### 1. 一份「什麼會安靜地壞掉」的失效形狀目錄

這是這個平台真正的產出。它們在任何技術棧上都成立：

| 形狀 | 一句話 |
|---|---|
| **登記為存在，但不執行** | `.gitignore` 規則對已追蹤的檔案無效；`ROTATION PASS` 掃過的是全豁免集合；容器 Up 而管線二十一小時沒收到任何一行 |
| **空集合上的恆真句** | 「每一個 X 都合規」在 X 為空時必然為真。所以四支工具一律 exit 2 拒答，不回報「沒有發現問題」 |
| **被呼叫不等於找得到** | 九支能力被程式碼呼叫著，而沒有人找得到；其中四支是人要手動執行的 |
| **可達不等於還是真的** | 傷最重的那份文件從 README 連得到、被標成「先看這份」，而它說反了 |
| **產生式 vs 手工承諾** | 漂亮但手工維護的現況頁，日後就失去維護 |
| **兩份索引是分岔問題不是重複問題** | 沒有人會同時更新兩份，於是其中一份開始說謊，而它讀起來和另一份一模一樣 |
| **設計上就是紅的檢查會被靜音** | 所以「從未使用的租戶」只報告不判失敗；所以重複偵測不做相似度評分——**誤報是檢查被靜音的方式** |
| **註解描述的機制不等於機制存在** | compose 註解寫著「明確設定以免落到錯的租戶」，而它用的值造成的正是那件事 |

**腳本會被換掉，這張表不會。** 換一套技術棧重寫這個平台，
第一天要帶過去的就是這張表——不是那 91 支腳本。

### 2. 證據紀律：每個量測宣稱都附可重跑指令，而那指令必須指向存在的東西

這是**協議，不是工具**。它的執行者今天是 `decisions.py`，明天可以是別的東西，
規則本身不變：

> 三個月後的問題從來不是「我們決定了什麼」，是「那個數字在哪、我怎麼再拿一次」。
> 找不到就沒有人重跑，於是憑印象重估——**而重估是一個穿著量測外衣的猜測**。

配套的是決策紀錄裡**量測與判斷分開寫**。工具迭代之後，
後人需要知道哪些要重新量（數字可能變了）、哪些要重新決定（取捨可能變了）。
混在一起寫，兩種都得重做。

### 3. 每個守衛都有一個證明它會變紅的合成控制項

**這一項最少見，也最難複製。**

大部分平台有測試。很少平台有「證明測試會失敗」的測試——
而**沒有被證明能失敗的守衛，和不能失敗的守衛，從輸出上分不出來**。
這個 repo 的每一支守衛都帶合成控制項：偽造一個孤兒、偽造一條斷鏈、
餵一棵只有一份文件的樹、注入一個打錯字的資料類別、
重建「DevOps 流程圖 vs DevOps 流程」那個真實事故。

控制項用合成資料與環境變數注入，不改真實檔案——
**因為一個中斷的測試不該讓 repo 留在壞掉的狀態**。

### 一句話

**這個平台的價值不是那 91 支能力，是那份「什麼會安靜地壞掉」的清單，
加上「每個宣稱都附重跑指令」的紀律，加上「每個守衛都被證明過會紅」。**
前者是知識，後兩者是習慣。**工具換掉之後，剩下的就是這些。**

## 四層目前涵蓋不到的（已知，刻意不現在做）

記在這裡是為了不被重新發現一次。**這些不是待辦事項**——
現階段的方向是收斂，不是加東西。

### 1. 可達性只看得到「檔案」，看不到「正在跑的東西」

四層走的是 git 追蹤的文件與原始碼。它們**完全看不到**：
執行中的容器、launchd job、K8s 工作負載、Grafana 儀表板、Vault policy。

**而這個平台最典型的失效就住在那一層**：排程器有 **7 個 job 從未觸發過**
（`audit` / `backup` / `dast` / `sast` / `restore` / `rotation` / `dastcov`）。
它們登記了、找得到、有四欄描述、沒有重複——**而它們沒有在跑**。
可達性四層全部給它們滿分。

**一張沒有人找得到的 Grafana 儀表板，是完全一樣的缺陷**，而四層都看不到它。

### 2. 沒有東西記錄「為什麼刪掉」

刪除留在 git 歷史裡，加上 README 的一段說明——而**下一次整理 README 的人會把那段刪掉**。
決策紀錄 0009–0012 記的全是「新增了什麼」，**沒有一筆記「刪掉了什麼、為什麼」**。
三份被刪的頁面（`System-State.html`、`Platform-Report.html`、八張手繪 SVG）
目前的耐久形式只有 commit message。

### 3. 可達性是靜態的：沒有時間，也沒有負責人

一份文件可以同時滿足「可達、產生式、有描述、不重複」，
而且**十八個月沒有人看過**。`--tree` 右欄有天數，但**沒有任何東西要求誰去看它**。
缺的性質不是「多久沒動」，是「**誰負責看它**」。

### 4. 描述可以在三欄仍然填滿的情況下變錯

第 3 層驗的是結構（能力是該列主詞、至少四格），
它**驗不了那三欄還對不對**。一支腳本改了行為而表格沒改，四層全過。
目前唯一的防線是量測宣稱的重跑指令紀律，而**那條紀律覆蓋數字，不覆蓋描述**。

### 5. 守衛自己也會腐爛，而檢查守衛的只有它們自己的控制項

控制項證明守衛**在寫的當下**會紅。沒有東西定期重新證明這件事。
突變測試（`~/Apps/AIS/capabilities/scripts/mutate`）是對的工具，
但**沒有接到這四支上**。

### 6. 三個知識表面，只有一條邊界規則

repo、AIS `capabilities/`、記憶目錄，三個表面。
上一節寫下了 repo 與 AIS 的邊界，**記憶目錄那一條沒有寫**，
而且沒有任何跨表面的檢查。

## 怎麼一次跑完四層

```bash
python3 platform/docs/doc_graph.py --check
python3 platform/docs/doc_freshness.py --check
python3 platform/docs/capability_graph.py --check
python3 platform/docs/duplicate_check.py --check
```

守衛在 `platform/tests/` 底下同名的四支套件裡，
全部登記在 `platform/tests/run_all.sh` 的 tier 1，**每一支都帶合成控制項**——
一個從來沒有紅過的檢查，和一個不會紅的檢查，分不出來。
