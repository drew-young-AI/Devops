三、擴充與收斂決策點

給需要決定投入方向的人。左欄按「不做的代價」排序，不是按技術難度。

值得擴充

依「不做的代價」由高至低

  1. 不可竄改封存（WORM） 稽核軌跡、evidence、git history 三者現在都存在，但三者都可被改寫——有 repo 寫入權就能把 FAIL 改成 PASS，有 root 就能改稽核日誌。這是讓所有紀錄從「我們說有」變成「可被證明」的那一層。
  2. 遮罩規則 v2 機制已上線並實測有效，但 v1 只涵蓋三種高信心樣式；自由文字中的姓名、地址、非預期格式的識別碼仍會原樣落地。
  3. Database change management 接向量資料庫/embedding 前必須具備，否則第一次 schema 變更就是停機事故。目前全平台唯一完全沒有對應機制的高風險項。
  4. 備份異地化 備份、還原演練與每日排程都已可用，但檔案與來源仍在同一顆磁碟。磁碟故障會同時失去兩者，排程並不能解決這一點。
  5. Grafana org 分隔落實 restricted 資料源已獨立佈建，但仍與一般資料源同在預設 org，任何已登入者都能存取。需要第二個真實使用者才有意義。

建議收斂或延後

已建置但目前產出價值低於維護成本

  1. Cosign 簽章 已建且驗證有效，但會把 hash 與時間戳發布到公開且不可刪除的 Sigstore Rekor。單機環境下價值低於揭露風險，目前已預設關閉——維持關閉即可。
  2. OpenTofu IaC 已建但無雲端 provider 可 apply，目前僅作為驗證與 policy gate。在雲端方案定案前不宜再投入。
  3. 分散式追蹤 只有一個服務，沒有跨服務呼叫可追。服務數超過 2 個再引入。
  4. Canary 與 Feature flag Blue/Green 對目前流量規模已足夠。
  5. 服務目錄與自助供裝 單人團隊、單一服務下屬於過早最佳化。服務數達 3+ 再評估。

五、驗證狀態

已驗證：告警四種判定（真實停機注入）、身分邊界 14 項（真實 token 真實請求）、 Vault 最小權限 8 項、LLM 複審確定性（6 次執行結果一致）與 5 種降級情境、 平台測試 5 個 suite 共 136 項、Gitleaks 全歷史掃描、還原演練 9 項 （於獨立容器解封 Vault 並讀回真實 secret，正式 Vault 全程未觸碰）、 Log 治理端到端（產生真實格式 PII，確認寫入即遮罩、跨租戶查詢 0 筆、無 header 一律 401）、 Grafana 認證雙向確認（Vault 憑證可用且 admin:admin 已失效）。

未驗證（標記為 UNVERIFIED）：LLM 複審的品質——確定性有量測， 但沒有已知缺陷回歸集，因此「模型抓得到真缺陷」尚無證據。遮罩對真實醫療 log 的 覆蓋率——機制已驗證有效，但只測過自己構造的樣本，未對真實資料量測漏網率。 Grafana 與 Alertmanager 的備份只做完整性檢查，未做還原演練。

本文件的狀態標記依據實際執行結果，非依據程式碼是否存在。 近期開發中共發現 12 個真實缺陷，全部只有在實際執行某條路徑時才會現形， 程式碼審查完全看不出來。因此「已實作」不等於「已可用」，本文件只採用後者。

每一道 gate 都以雙向實測驗收：不只證明它對正常輸入放行， 更要證明它對「刻意做壞的輸入」確實會擋。SAST 用故意寫的注入漏洞、 DAST 用刻意缺標頭的頁面、Trivy 用較舊的映像、還原演練用真實解封讀取。 只驗證放行方向的 gate 無法區分「守住了」與「根本沒在看」。

排程之後，「沉默」不再等於「正常」。排程器最危險之處在於 它的失效模式就是安靜——沒載入、plist 壞掉、PATH 錯誤，結果都不是警報而是 無聲，而無聲正是健康系統的樣子。因此新鮮度由消費端檢查： 每個 job 記錄自己何時執行，超過兩倍間隔即成為可見的 STALE 狀態， 且陳舊性凌駕記錄的狀態——四天前回報 ok 的 job 不是 ok， 是一個過期的宣稱。

同一類缺陷出現三次後，就把它變成 build 會擋的檢查。 docker exec -i 會接管呼叫者的 stdin，這在本平台造成過三次事故： 還原演練的 unseal 迴圈被吃掉金鑰而停在 1/3（無任何錯誤訊息）、稽核查詢每次 回傳零筆（heredoc 覆蓋了管線）、身分驗證整套卡死七分鐘。三次就不是巧合而是 類別，現已加入靜態檢查——未明確關閉 stdin 的 docker exec -i 一律讓測試失敗，且該檢查本身也做過負向驗證。
