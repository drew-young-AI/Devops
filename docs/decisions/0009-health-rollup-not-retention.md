# 0009 健康快照用彙總收斂，不用保留策略刪除

## 決定

`evidence/observability` 累積的健康快照，**用一支彙總腳本收斂成一份可查詢的答案，
一份都不刪**。實作在 `platform/observability/rollup_health.py`，每小時跑一次，
輸出 `evidence/observability/health_rollup.json` 與
`evidence/statusdag/health_rollup.prom`。

這不是新方向，是**執行 ADR-0006 已經寫下但沒做的處方**。

## 這條決策怎麼來的

2026-09-01 檢討「1,519 個未提交／已追蹤的快照該怎麼辦」時，第一個提出的方案是
**保留策略：只留最近 N 天**。那個方案是錯的，而且 ADR-0006 的「明確不做」一節
已經逐字禁止過：

> 不對 `evidence/` 做保留刪除。刪掉的是可追溯性，而可追溯性是 README 第二節的整個重點。
> **收斂要用彙總，不是用 `find -mtime -delete`。**

**先讀既有決策，再提新方案。** 這條記在這裡，因為錯的不是判斷力不足，
是根本沒去查平台自己早就寫下的結論——而平台寫決策記錄的全部意義就是不要重犯。

## 量到什麼

第一次對真實證據執行（1,520 份快照，2026-08-13 至 09-01，耗時 0.12 秒）：

| 指標 | 值 |
|---|---:|
| 快照總數 | 1,520 |
| **監測涵蓋率** | **83.6%**（應有 1,818 份） |
| 判定為 UNKNOWN（監測本身壞掉） | 259 |
| 判定為 DEGRADED | 269 |
| 無紀錄空窗次數 | 54 |
| 最長無紀錄空窗 | 25.9 小時 |
| **最長連續中斷** | **73.7 小時** |

重跑：`python3 platform/observability/rollup_health.py`

### 那 73.7 小時

**2026-08-21T13:41Z 至 2026-08-24T15:25Z，Prometheus 與 Alertmanager 同時
拒絕連線（Errno 61）。** 健康探針每 15 分鐘忠實地把這件事寫進證據，
連續寫了三天，約 200 份。**沒有人打開過任何一份。**

這正是 ADR-0006 的論點，只是那時它只有 11 小時的版本（`WidespreadGeoDrift`
每個週期評估失敗）。彙總同時獨立測到那一段：`alert_rules_evaluating`
最長連續中斷 38,638 秒 ＝ 10.7 小時。**兩個獨立來源對上了同一個事件。**

### 涵蓋率為什麼是重點

83.6% 的缺口不是「那段時間是好的」，是**「那段時間沒有人在看」**。
所以彙總把兩者分開計算，不相加：

- **連續中斷（episode）**：看了，是壞的 → 是證據
- **無紀錄空窗（gap）**：根本沒看 → 不是證據

把兩者加總會得到一個沒有意義的數字。單一份快照永遠測不到空窗，
因為快照只能陳述它被寫下的那一刻。

主要成因是筆記型電腦休眠（§5c 的宿主現實），不是缺陷；
但它必須是**看得見的數字**，而不是默默消失的分母。

## 為什麼是「一份都不刪」

刪掉舊快照就刪掉了上面那三段分析賴以成立的東西。5.9 MB／三週的成本，
換的是「這件事到底壞了多久」在事故當下答得出來。

真正的問題從來不是檔案數量，是**沒有人會讀 1,520 個結構相同的檔**——
而讀了兩個就外推全體健康，正是 grounding gap 穿著證據的外衣。
彙總解決的是這個，保留策略解決的是磁碟，而磁碟不是問題。

## 呈現在哪裡

- **Grafana**「三線階段燈號」新增一列（面板 100–104）：涵蓋率、最長連續中斷、
  空窗次數、各檢查失敗數、判定分布
- **Prometheus** 新增 `PlatformHealthRollupStale`：彙總本身停掉時，
  涵蓋率會凍結在最後一個數字，看起來像「沒有新問題」

第二條的理由與 `PlatformBoardStale` 相同：node-exporter 會繼續提供最後讀到的
textfile，**凍結的綠燈和健康的綠燈長得一模一樣**。

## 明確不做

- **不刪任何快照。** 與 ADR-0006 一致。
- **不對涵蓋率設告警。** 它是全期累計值，只會單調變化，設了會永遠響或永遠不響。
  當下的健康由 `PlatformNodeFailed` 與 `check_health.sh` 負責，
  這份彙總是歷史視圖。
- **不引入 DuckDB／parquet。** 純標準函式庫，0.12 秒，
  加一個相依只會讓 CI 多一個裝不起來的東西——而這正是雙架構那份決策
  （ADR-0008）剛付過學費的地方。

## 什麼時候回頭

- 彙總耗時超過 5 秒（目前 0.12 秒，代表快照數成長約 40 倍）
- 需要「任意時間窗」而非全期的查詢 → 那時才是欄式儲存的場合（ADR-0001 的形態）
- 涵蓋率長期低於 80% → 那不是彙總的問題，是排程宿主的問題
