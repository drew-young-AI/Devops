# 0012 可觀測性：應用端一律 OTLP，後端選型延後

## 決定

1. **應用端一律輸出 OpenTelemetry（OTLP）**。這是契約，不是工具選擇。
2. **追蹤（traces）與錯誤追蹤（error tracking）後端現在不選、不裝。**
3. **在 span 屬性的遮蔽做完之前，不開啟 OTLP 接收端。** 理由見下，這條是硬的。
4. 現有的 metrics／logs 路徑不動。

## 先修正一個在流傳的對應表，因為它錯得會誤導選型

被提出的對應是「Prometheus、Grafana、Jaeger、SigNoz ＝ 指標、日誌、追蹤、錯誤」。
**四格裡有兩格是錯的，而且錯法不同。**

| 說法 | 實際 |
|---|---|
| Grafana ＝ 日誌 | **Grafana 不儲存任何東西**，它是查詢與呈現的介面。[Loki 才是 Grafana 生態系中負責儲存與查詢 log 的核心組件](0011-loki-not-elk.md) |
| SigNoz ＝ 錯誤 | SigNoz 是 **OTel 原生的全棧後端**（metrics + logs + traces 一套），它是**取代** Prometheus + Loki + Jaeger 的選項，不是排在它們旁邊的第四格 |
| 「錯誤」這一格 | 那是 **Sentry** 類產品的位置：錯誤分組、去重、綁定版本與 release、回溯到某次部署。**它和 traces 解的不是同一個問題**，也不能由 traces 替代 |

**正確的現況對應**（這是量測，不是分類學）：

| 支柱 | 目前 | 狀態 |
|---|---|---|
| 指標 | Prometheus | 在跑 |
| 日誌 | **Loki** | 在跑，[已量測 72,331 行／116 串流](0011-loki-not-elk.md) |
| 追蹤 | — | **完全沒有** |
| 錯誤追蹤 | — | **完全沒有** |
| 採集器 | **Grafana Alloy v1.10.2** | 在跑（見下，這一列是關鍵） |
| 介面 | Grafana | 在跑，唯一需要驗證身分的入口 |
| 告警 | Alertmanager | 在跑 |

## 可觀測性拆成六個元素，OpenTelemetry 只涵蓋前三個

「OTel 會統一可觀測性工具」這句話**是半對的，而錯的那一半正好是最貴的那一半**。
把可觀測性拆開來看就清楚了：

| # | 元素 | 誰在做 | OTel 涵蓋？ |
|---|---|---|---|
| 1 | **儀器化**（instrumentation）——應用程式裡實際產生訊號的那段程式 | OTel SDK / auto-instrumentation | **是** |
| 2 | **傳輸格式**——訊號怎麼在線上走 | OTLP | **是** |
| 3 | **採集器**——接收、批次、取樣、遮蔽、路由 | OTel Collector（**Alloy 就是它的一個發行版**） | **是** |
| 4 | **儲存後端**——每種訊號各自存在哪 | Prometheus / Loki / Tempo / Jaeger / SigNoz… | **否，而且永遠不會** |
| 5 | **查詢語言** | PromQL / LogQL / TraceQL / SQL | **否** |
| 6 | **儀表板與告警** | Grafana / Alertmanager | **否** |

**OTel 專案的範圍明確排除 4、5、6**——它不做儲存，這是它的設計宣告，不是還沒做到。

所以你的原意（**不要現在選工具與後端**）是對的，而且 OTel 正是達成它的方法。
但要精確一點：**不是「不用選」，是「選得晚、而且選錯換得起」。**
訊號終究要落到某個地方；OTel 買到的是**把那個決定推到最後、而且讓它可逆**。

### 貴的那一半在哪裡

元素 1 是**最貴、最侵入、最難重做**的：它要動到每一個服務的程式碼。
**這正是 OTel 值得現在就定下來的唯一理由**——把最難改的那層做成廠商中立，
之後換 4、5、6 只改採集器設定，應用程式一行不動。

元素 5、6 是**換後端時真正的成本**，而 OTel 完全不碰它們：
PromQL 寫的告警規則搬不到 TraceQL，Grafana 的儀表板搬不到 Kibana。
**這是實質鎖定，而且它不會因為採用 OTel 而消失。**
唯一的減災是**把儀表板與告警規則當程式碼管理**，讓它們至少是可被重寫的文本，
而不是散在某個 UI 裡沒人知道有幾張。

### 語意慣例是被低估的那一項

OTel 還給一樣東西：**共用詞彙**（semantic conventions）——`http.request.method`
在每個服務、每個語言、每個後端都是同一個意思。
沒有它，「統一」只是「用同一條線傳不一樣的東西」。

代價是它**仍在演進**，跨版本的屬性改名會讓既有查詢對不上。
**做法是在採集端釘住版本**，不要讓每個服務各自決定——
否則你會得到三個服務、三套命名，而那正是 OTel 要解的問題本身。

### OTel 不是免費的（這三項要講清楚）

1. **SDK 有執行成本**：取樣不是可選項，是必須設定的東西。
2. **採集器是多一個要監控的程序**——而**一個安靜死掉的採集器，
   看起來就像「今天沒有什麼事發生」**。這正是這個平台反覆遇到的形狀
   （Loki 收了二十一小時的 log，沒有任何東西檢查過它有沒有在收）。
   採集器一旦承載訊號，它自己就必須有健康證據。
3. **採集器是全系統最高價值的攻擊目標**：所有訊號在**遮蔽與路由之前**都經過它，
   它看得比任何單一後端都多。**這是把遮蔽放在採集器裡的理由**（log 已經是這樣做的），
   也是它必須有自己的存取邊界的理由。

## SigNoz：不選，理由不只是成本

**成本是次要的，結構才是主要的。** SigNoz 是 OTel 原生的全棧後端
（metrics + logs + traces 一套），它**取代** Prometheus + Loki + Jaeger，
而取代掉的東西裡有一個這個平台已經擁有、且不打算放棄的性質：

> **restricted 日誌對某個資料源是「結構上不可達」**——Loki 以租戶
> （`X-Scope-OrgID`）在**每個請求上**強制隔離，保留期 platform 168h／restricted 72h。

把三種訊號併進單一程序、單一認證邊界，等於把那個性質換成
「查詢時記得過濾」。**承諾不是控制。**

而且——**現在不選它，以後也不會更難選**。這正是 OTel 決定的回報：
應用端已經是 OTLP，換後端只是改採集器的輸出端。
**拒絕一個全棧方案的代價，因為採用了 OTel 而趨近於零。**

## 「應用端一律 OTel、後端延後」——這個結論對，而且比想像的更便宜

**Grafana Alloy 就是 OpenTelemetry Collector 的一個發行版，而它已經在跑了。**
現在它只做 Docker log 的採集與遮蔽（`loki.source.docker` → `loki.process` → `loki.write`），
但同一個程序本來就能收 OTLP 並分流到 Prometheus／Loki／Tempo。

所以「應用端一律 OTLP」的代價**不是多一個元件，是一個 `otelcol.receiver.otlp` 區塊**。
後端換掉時要改的是 Alloy 的輸出端，應用程式一行都不用動。這正是延後選型的價值所在。

## 但「省事」要拆開講：OTel 帶得走的和帶不走的

**帶得走**：wire protocol、SDK、instrumentation 程式碼。這是真的，也是主要的價值。

**帶不走**（換後端時真正的成本在這裡）：

1. **語意慣例（semantic conventions）漂移**。屬性名稱在 OTel 規格裡仍在演進，
   跨版本查詢會對不上。**要在採集端釘住版本，不要讓每個服務各自決定。**
2. **Collector 管線設定**。取樣、批次、遮蔽規則、路由——這是每次換後端都要重寫的部分。
3. **查詢、儀表板、告警規則**。PromQL / LogQL / TraceQL 之間不可攜。
   這是最大的一塊，**所以儀表板必須當程式碼管理**，否則它就是換後端的實質鎖定。

「省事」成立在第一項，不成立在後三項。延後選型是對的；把延後當成「以後無痛」是錯的。

## 安全：這是延後的最強論據，也是不要選全棧的論據

可觀測性系統把整間公司的內部狀態集中到一處，**它本身就是高價值目標**。這個判斷正確。

目前這個平台在那件事上有一個**結構性**的性質，值得在選型時當成硬需求：

> **restricted 日誌對某個資料源而言是「結構上不可達」，不是「查詢時被過濾掉」。**
> Loki 以租戶（`X-Scope-OrgID`）在每個請求上強制隔離，指向 `platform` 租戶的資料源
> 不可能回傳 restricted 資料。保留期也不同：platform 168h／restricted **72h**
> （敏感資料保存**更短**不是更長）。

**任何未來的後端，如果做不到「結構上不可達」而只能做到「查詢時過濾」，就不要選。**
查詢時過濾是一個「所有查詢的人都會記得套用」的承諾，而承諾不是控制。
把 metrics + logs + traces 併進單一程序、單一認證邊界的全棧方案（SigNoz 屬此類），
必須先回答這個問題才能進入評估。

## 為什麼「先把 OTLP 接收端打開」不是安全的第一步

**追蹤是這三種訊號裡 PII 風險最高的一種，而目前的遮蔽完全沒有涵蓋它。**

span 屬性例行性地帶著完整 URL、query string、使用者識別碼、SQL 片段。
現有的 `loki.process` 遮蔽 v1 是**針對 log 行**寫的三條高信心樣式
（台灣身分證、email、憑證型 token），**它不會處理 span 屬性**，
而追蹤資料進入儲存後，唯一真正的補救同樣是重建整個 store。

所以順序是**先遮蔽、後接收**，不是「先收起來再說」。這與 log 遮蔽當初的判斷一致：
這是全平台唯一「晚做比做得不完美更貴」的機制類別。

## 現在要做的（基本款）＝ 只有這一項

**把契約與前提寫下來，並且讓它找得到。** 不裝 Tempo、不裝 Jaeger、不裝 SigNoz、不開接收端。

理由不是保守，是這個平台自己的規則：一個沒有人在用、沒有證據流過的元件，
[讀起來和正在運作的元件一模一樣](0011-loki-not-elk.md)——
Loki 在被量測之前就處在那個狀態整整二十一小時而沒有人知道。**多一個那樣的元件是負資產。**

## 開始做追蹤之前必須先成立的三件事（依序）

1. **遮蔽擴及 span 屬性**：`loki.process` 的規則搬進 `otelcol.processor`，
   並以合成 PII 端到端驗證（與 log 遮蔽當初同一種驗法：產生真實格式的 PII，
   確認儲存內容是 `[REDACTED_*]`，且原始值在所有租戶查詢皆 0 筆）。
2. **租戶隔離的等價物**：追蹤後端必須能做到「結構上不可達」。做不到就不選。
3. **有一個真的需要追蹤的問題**：目前是單一 Pilot、單一資料庫。
   追蹤解的是**跨服務的因果與延遲歸因**，服務數量到位之前，它解的問題還不存在。

## 觸發重審

- 服務數量到達「一次請求跨三個以上服務」——那時追蹤才開始有它要解的問題
- k3s 上出現跨 Pod 的延遲歸因需求（[ADR-0010](0010-kubernetes-target-runtime-k3s.md)）
- 錯誤追蹤（Sentry 那一格）出現真實需求：需要把例外綁定到 release 與部署
- 任何一方要求「所有訊號在同一個 UI」而願意接受單一認證邊界的風險

## 哪些是量測、哪些是判斷

- **量測**：Alloy v1.10.2 在跑、`config.alloy` 沒有任何 OTLP 接收端、追蹤後端不存在。
  Loki 的 72,331 行／116 串流以 `platform/observability/loki_coverage.py` 重跑可得。
- **判斷，無法量測**：「先遮蔽後接收」的順序、全棧方案的風險評估、
  以及「服務數量不足以讓追蹤有意義」。這些是取捨，不是數字。
