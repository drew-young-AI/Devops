# ADR-0019：守衛是一份「過去失敗清單」，不是覆蓋集合

## 被問到的問題

「為什麼每一次都能抓出很多 gap、bug、mismatch？似乎舊方法不能維持品質。」

這個問題是對的，而且它指出的不是執行不力，是**方法的結構性上限**。

## 量測

2026-09-10 一個 session 內找到的缺口，全部是「有可用的腳本或指標、而板面沒有節點」：

| 表面 | 既有的東西 | 缺的 |
|---|---|---|
| 憑證到期 | `openssl` 讀得到，三張憑證都在 repo 裡 | **整個平台沒有任何地方檢查過** |
| 主機磁碟 | `host_disk_metrics.sh` 每 5 分鐘寫指標 | 沒有節點 |
| 機密輪替覆蓋率 | `check_rotation_sweep.sh` 印 `checked 1 of 3` | 沒有節點，也沒有留證據 |
| IaC | `tofu validate` 可跑、CI 也在跑 | 沒有節點（README 自己記了好幾個月） |
| 來源是否仍在發布 | 指標與告警規則都有 | 沒有節點；`sources` 只數登記筆數 |
| 生產節點健康 | kubelet 的條件與 stats 端點 | 沒有節點；`prodk8s` 綠著也可能是磁碟滿的機器 |
| 分析鏡像一致性 | `mirror_manifest.json` 有 watermark | 沒有節點 |
| 日誌真的有進來 | `loki_coverage.py` 每次都在跑 | 沒有節點；`loki` 只看容器活著 |

同一天另外找到四份文件的過期宣稱（其中一句「還沒接通知收件端」在接上之後
**又留了三個星期**），以及 Telegram 連續三天 74% 送不出去而沒有任何地方看得出來。

## 根因

**這個 repo 的每一個守衛都是在某次失敗之後寫的。**

那讓守衛集合成為一份**過去失敗的清單**，不是一個覆蓋集合。它的成長方式是
「有人剛好看到」，而不是「母體被列舉過」。於是：

- 每一輪 review 都會找到新東西——因為上一輪找到的是**上一輪剛好看到的**那些。
- 找到多少，取決於誰在看、看多久、以什麼順序看。**這是可重現性為零的流程。**
- 再寫一支測試不會改變這件事：它只是在清單上多加一筆過去的失敗。

第二個根因是**測試回答的問題不對**。測試回答「這個東西壞了嗎」。
沒有任何測試回答「**有沒有東西是沒有人在問這個問題的**」。
只有第二個問題會讓未知集合自己縮小。

## 決定

**加入一個對母體的封閉檢查（closure check），而不是再加一支測試。**

`platform/tests/test_coverage_closure.sh`：

1. **列舉母體**：每一份 compose 宣告的服務、`jobs.conf` 裡的每一個排程 job。
2. **要求每一個都被宣告**：對應到 `dag.py` 的 `COVERAGE` 裡的一個板面節點，
   或者寫在 `UNMEASURED` 裡**附上理由**。
3. **兩個方向都檢查**：多出來的（有東西沒被宣告）與少掉的（宣告了一個已經
   不存在的東西——那代表登記簿自己過期了）。
4. **列舉為空即拒絕**：列不到 10 個表面就是列舉壞了，不是平台變乾淨了。

重跑：

```bash
bash platform/tests/test_coverage_closure.sh
```

實測：往 `jobs.conf` 加一行 `newthing|3600|60|platform/observability/check_health.sh`，
套件從 11 passed 變成 10 passed / 1 failed（`UNDECLARED job:newthing`）；
還原後 11 passed，`diff` 確認檔案位元組相同。

**明天新增一個服務或一個 job，這支會紅到有人說出它在哪裡被量。**
發現不再是運氣。

## 這個決定刻意不做的事

**不要求每個表面都被量測。** 今天有 9 個表面是 `UNMEASURED`，每一個帶一句理由
（node-exporter、alloy、health、board、dag、stagereport、rollup、dastcov、catalog）。

**「沒有量」和「決定不量」必須長得不一樣。** 寫下理由的是決定；只是不存在的，
正是這份登記簿要擋掉的東西。

## 三個被否決的替代方案

| 方案 | 為什麼否決 |
|---|---|
| **再多寫測試** | 這正是產生問題的方法。清單變長，覆蓋率不變 |
| **產生程式碼補齊每個節點** | 使用者明確指出「gen code 堆積是錯誤」。八個新節點是**接到既有腳本與既有指標上**，沒有一個是新造的機制；堆出來的程式碼會讓母體變大而不是變清楚 |
| **一次性的全樹稽核** | 做過，就是這一輪。它會過期，而且下一次仍然取決於有人有空 |

## 兩份登記簿合起來才是封閉的

| 母體 | 誰列舉 | 要求 |
|---|---|---|
| **腳本**（102 支能力） | `platform/docs/capability_graph.py` | 每一支都要被一份點得到的文件描述到，零孤兒 |
| **服務與排程 job**（33 個） | `test_coverage_closure.sh` | 每一個都要對應到板面節點，或寫下為什麼沒有 |

兩份都是對母體的封閉檢查，不是對行為的測試。腳本那一份問「有沒有人**寫下**它」，
服務那一份問「有沒有人**在量**它」。「有腳本、沒節點」正好是掉在兩份之間的縫，
第二份補上之後那條縫關起來了。

## 這個方法的邊界（誠實說出來）

封閉檢查只覆蓋**它列舉得到的母體**：容器與排程 job。它抓不到：

- **文件的過期宣稱**（例如「還沒接收件端」）——沒有可列舉的母體。
  目前的部分解法是 §零 的守衛：文件宣稱缺某個檔案時，驗證同一列指名的腳本
  真的會產生那個檔案。
- **量測本身是對的但門檻是錯的**（`cdc-tb-caremag` 的 3 天門檻來自發布者自己
  宣稱的每日）——登記在 Backlog T35。
- **一個節點量了東西但量錯對象**——這只有合成控制項擋得住，
  所以每個新節點都必須有讓它變紅的控制項。

換句話說：這一份 ADR 把「有沒有人在問」變成機械化的，
把「問得對不對」留給合成控制項，而**兩者都不保證「答案還是真的」**——
那是可達性紀律（ADR-0018）的工作。
